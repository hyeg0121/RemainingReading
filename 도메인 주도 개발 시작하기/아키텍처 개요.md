
## 2.2. 계층 구조 아키텍처 

계층 구조는 그 특성상 상위 계층에서 하위 계층으로의 의존만 존재하고 하위 계층은 상위 계층에 의존하지 않는다. 계층 구조를 엄격하게 적용한다면 상위 계층은 바로 아래의 계층에만 의존을 가져야 하지만 구현의 편리함을 위해 계층 구조를 유연하게 적용하기도 한다.

## 2.3. DIP
DIP=Dependency Inversion Principle (의존 역전 원칙)

인프라스트럭처에 의존하면 테스트 어려움과 기능 확장의 어려움이라는 두 가지 문제가 발생한다. DIP는 이를 해소할 수 있는 방법이다.

고수준 모듈은 의미있는 단일 기능을 제공하는 모듈로 고수준 모듈의 기능을 구현하려면 여러 하위 기능이 필요하다. 저수준 모듈은 하위 기능을 실제로 구현한 것이다. 따라 고수준 모듈이 제대로 동작하려면 저수준 모듈을 사용해야 한다. 그런데 고수준 모듈이 저수준 모듈을 사용하면 구현 변경과 테스트가 어렵다는 문제가 생긴다.

DIP는 이 문제를 해결하기 위해 저수준 모듈이 고수준 모듈에 의존하도록 바꾼다. 이를 구현하는 방법은 추상화한 인터페이스이다. 

``` java
// interface
public interface RuleDiscounter {
	Money applyRules(Customer customer, List<OrderLine> orderLines);
}
```

여기서 RuleDiscounter는 고수준 모듈에 속한다. DroolsDuleDiscounter는 고수준의 하위 기능인 RuleDiscounter를 구현한 것이므로 저수준 모듈에 속한다. DIP를 적용하면 저수준 모듈이 고수준 모듈에 의존하게 된다.  

DIP를 적용할 때 하위 기능을 추상화한 인터페이스는 고수준 모듈 관점에서 도출한다. 

인프라스트럭처 영역은 구현 기술을 다루는 저수준 모듈이고 응용 영역과 도메인 영역은 고수준 모듈이다. 인프라 스트럭처 계층이 가장 하단에 위치하는 구조와 달리 아키텍처에 DIP를 적용하면 인프라 스트럭처 영역이 응용 역역과 도메인 영역에 의존하는 구조가 된다.

인프라 스트럭처에 위치한 클래스가 도메인이나 응용 영역에 정의한 인터페이스를 상속받아 구현하는 구조가 되므로 도메인과 응용 영역에 대한 영향을 주지 않거나 최소화하면서 구현 기술을 변경하는 것이 가능하다.

## 2.4. 도메인 영역의 주요 구성 요소

Entity
- 고유의 식별자를 갖는 객체로 자신의 라이프사이클을 갖는다.
- 주문, 회원, 상품과 같이 도메인의 고유한 개념을 표현한다.
- 도메인 모델의 데이터를 포함하며 해당 데이터와 관련된 기능을 함께 제공한다.

Value
- 고유의 식별자를 갖지 안는 객체로 주로 개념적으로 하나인 값을 표현하기 위해 사용된다.
- 배송지 주소를 표현하기 위한  주소나 구매 금액을 위한 금액과 같은 타입이 밸류이다.
- 엔티티의 속성 또는 다른 밸류의 속성으로 사용될 수 있다.

Aggregate
- 에그리거트는 연관된 엔티티와 밸류 객체를 개념적으로 하나로 묶은 것이다. 예를 들어, 주문과 관련된 Order, OrderLine, Orderer 엔티티 또는 객체를 주문 애그리거트로 묶을 수 있다.

Repository
- 도메인 모델의 영속성을 처리한다. 예를 들어 DBMS 테이블에서 엔티티 객체를 로딩하거나  저장하는 기능을 제공한다.

Domain Service
- 특정 엔티티에 속하지 않은 도메인 로직을 처리한다.
- 할인 금액 계산을 예로 든다면 상품, 쿠폰, 회원 등급, 구매 금액 등 다양한 조건을 이용해서 구현하게 되는데, 이렇게 도메인 로직이 여러 엔티티와 밸류를 필요로 하면 도메인 서비스에서 로직을 구현한다.
