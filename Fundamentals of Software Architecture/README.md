# 1주차
### 02. 아키텍처 사고
**(1) 요약**
- 아키텍처 대 설계
	- 전통적으로 아키텍트와 개발자의 역할이 분리되있지만, 이분법적 접근이 아닌 양방향 소통이 필요하다.
- 기술 폭
    - N개의 솔루션을 알고 각 솔루션의 트레이드오프를 분석하는 것이 핵심이다.
- 트레이드오프
	- 모든 아키텍처 결정은 트레이드오프를 수반한다.
	- 따라 다양한 솔루션의 장단점을 분석하여 최선의 결정을 내려야 하는 과정이 필요하다.
- 비즈니스 동인의 이해
	- 아키텍처 설계를 위해서는 단순한 기술적 고려를 넘어 비즈니스 특성 또한 고려되어야 한다.

**(2) 의견**
- ADR, ATAM 등의 프레임워크를 적용할 수 없을까
	- 책에서 강조하는 트레이드오프에 대한 논의가 현재 활발하게 이루어지고 있나?
	- 의사 결정에 대한 과정, 구체적 설계 방안이 작성된 문서가 부족하다고 생각
		- 문서로 남기는 것이 중요하다고 생각한 이유는 - 당시에 어떤 제약이 있었는지, 이 방식이 최선이었던 이유가 무엇인지, 당시 논의되었던 이슈 - 들에 대해 파악할 수 있기 때문에
	- 우려되는 점 
		- ADR 작성의 범위(or 기준)을 확실해야 함. (기준이 애매하면, 애매한 의사결정에 대한 ADR 작성을 미루게 되고 결국 ADR 작성 문화 자체가 사라질 위험이 있음. 물론 아무리 확실하게 해도 모호한 것들은 존재할 수 밖에 없긴 하겠지만)
			- -ADR이 필요한 결정 vs 불필요한 결정-에 대한 가이드라인 또한 필요
