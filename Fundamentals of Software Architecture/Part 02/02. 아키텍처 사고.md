아키텍트의 사고 방식은 크게 네가지로 나뉜다.
```
1. 아키텍처와 설계의 차이를 이해하고 아키텍처 작업을 진행하려면 개발팀과 어떻게 협력해야 할지 아는 것
2. 어느정도 기술 깊이를 유지하면서 폭넓은 기술 지식을 확보하는 것
3. 다양한 솔루션과 기술 간의 트레이드오프를 이해하고, 분석하고, 조율하는 것
4. 비즈니스 동인의 중요성을 이해하고 그것을 아키텍처 관심사로 해석할 줄 아는 것
```

### 2.1. 아키텍처 대 설계

- 아키텍트처럼 사고한다는 것은 비즈니스와 기술 문제를 해결하기 위해 아키텍처와 설계의 차이점을 알고 이 둘을 긴밀하게 통합한 솔루션을 모색하는 것이다.
- 전통적인 아키텍트의 책임과 개발자의 책임을 비교하자면
	- 아키텍터는 비즈니스 요구사항을 분석하여 아키텍처 특성을 도출하고 어떤 아키텍처 패텅과 스타일이 해당 문제 영역에 가장 알맞는지 선택하여 각종 컴포넌트 (시스템 구성 요소)를 만든다
	- 개발팀은 각 컴포넌트의 클래스 다이어그램을 그린 뒤 UI 화면을 만들고 소스 코드를 개발/테스트한다.
- 하지만 이 전통적인 아키텍트와 개발자의 역할은 문제가 있다.
	- 아키텍트와 개발자의 소통이 단방향적으로 이뤄지면 안된다.
- 제대로 된 아키텍처를 만들려면 반드시 아키텍트와 개발자를 가르는 장벽을 허물고 두 팀이 양방향으로 소통하는 관계를 정립해야 한다.

### 2.2. 기술 폭

- 업무를 진행하기 위해 기술 깊이를 확보해야 하는 개발자와 달리, 소프트웨어 아키텍트는 아키텍트 답게 사고하고 아키텍처 시각을 유지하기 위해 상당한 기술 폭을 갖춰야 한다.
- 지식 피라미드
	- 내가 알고 있는 것
		- 자바 프로그래머가 자바를 아는 것처럼 전문 기술자가 일상 업무 수행에 사용하는 기술, 프레임워크, 언어, 도구를 말한다.
	- 내가 모른다는 사실을 아는 것
		- 한번 들어봤거나 얕은 지식은 갖고 있지만 실무 경험은 거의 전무한 기술을 가리킨다.
	- 내가 모른다는 사실조차 모르는 것
		- 기술자가 해결하려는 문제에 완벽한 정답임에도 불구하고 그 존재조차 알지 못하는, 절대 다수의 프레임워크, 기술, 도구, 언어를 말한다.
- 전문적인 기술은 중요하기 때문에 내가 알고 있는 것을 넓히는 것은 본인에게 이롭지만 ‘내가 알고 있는 것’ = ‘내가 계속 유지해야 할 것’이기도 하다.
- 그러나 개발자가 아키텍트로 진로를 바꾸면 지식의 성격이 달라진다.
	- 아키텍트의 가치는 대부분 기술에 대한 폭넓은 이해와 그 기술을 사용해서 특정한 문제를 해결하는 것이다.
	- 즉, 아키텍트는 어니 한 가지 문제만 해결 가능한 한 가지 전문 지식보다는, 문제를 해결할 수 있는 다섯 가지 솔루션을 알고 있는게 더 중요하다.
	- 아키텍트에게는 깊이보다 폭이 더 중요하다.
		- 아키텍트는 기술적인 제약 하에 어떤 기능이 가장 알맞는지 결정해야 하므로 아주 폭넓은 솔루션을 두루 꿰고 있어야 한다.
```
꽁꽁 언 원시인 안티패턴
- 어떤 아키텍처든 언제나 가장 비합리적인 관심사로 회귀하려는 아키텍트를 말한다.
- 특수한 아키텍처 특성에 강박을 가져 새로운 아키텍처에 대해 경계하는 태도를 지양하자.
- 진짜 기술 리스크와 리스크처럼 보이는 기술 ㄹ스크의 차이를 이해하는 것은 아키텍트가 평생 학습해야 하는 주제이다.
- 아키텍트답게 생각하려면 꽁꽁 언 원시인의 사고 방식과 경험을 극복하고 다른 솔루션을 찾아보면서 더 적절한 질문을 해야한다.
```

### 2.3. 트레이드 오프 분석

- 아키텍트처럼 생각하는 것은 기술 여부와 상관없이 모든 솔루션의 트레이드오프를 분석하여 최선의 솔루션을 결정하는 것이다.
- 아키텍처는 모든게 다 트레이드오프다.
- 아키텍처적으로 사고하려면 각 방안의 트레이드오프를 분석하고 주어진 상황에서 가장 나은 선택을 해야 한다.
- 아키텍처 사고는 어떤 솔루션의 장점도 보면서 그와 연관된 단점이나 트레이드오프는 없는지 분석한다.

### 2.4. 비즈니스 동인의 이해

- 아키텍처 사고는 성공적인 시스템 구축에 필요한 비즈니스 동인을 이해하고 요구사항을 아키텍처 특성으 해석하는 것이다.
	- 확장성, 성능, 가용성 등의

### 2.5. 아키텍처와  코딩 실무 간 균형 맞추기

- 코딩 실무와 소프트웨어 아키텍처의 균형을 맞추는 것도 아키텍트가 해야하는 일이다.
- 병목 트랩(bottle neck)에 빠지지 말라
	- 병목 트랩은 아키텍트가 프로젝트의 크리티컬 패스(임계 경로, 최장 경로)에 있는 코드의 소유권을 갖고 있는 경우 발생한다.
	- 아키텍트는 풀타임 개발자가 아니므로 개발자 역할과 아키텍트의 역할의 균형을 잘 맞춰야 한다.
- POC(proof of concept)를 자주 해보자
	- 아키텍트가 소스 코드를 직접 작성하면서 구현 상세를 생각하게 되므로 아키텍처 결정을 검증하는데 유용하다
	- POC 작업을 할 때에는 가능한 한 프로덕션 수준의 고품질 코드를 작성하는 게 좋다.
- 개발팀이 아주 중요한 유저 스토리 작업을 할 수 있도록 기술 부채 스토리나 아키텍처 스토리에 전념하자.
-
